# Модуль всплывающего чат-бота ClickJurist

Автономный подмодуль сайта: отвечает посетителю на вопросы о сервисе —
тарифы, шаги работы, оплата, документы, защита данных. Начинается с
приветствия, показываемого при открытии страницы.

Модуль **не зависит** от основного приложения в одну сторону: если он не
подключён, сайт работает как раньше. Если подключён — добавляет
`/api/chatbot/*` и раздаёт виджет по `/chatbot/static`.

## Подключение

Уже выполнено в `backend/main.py` и `frontend/index.html`:

```python
# backend/main.py
from chatbot.app import register

register(app)
```

```html
<!-- frontend/index.html -->
<script type="module" src="/chatbot/static/js/chatbot.js"></script>
```

Виджет сам находит контейнер `#chatbot-slot`, если он есть на странице,
иначе создаёт свой в `<body>`.

## Архитектура

Слои зависят только внутрь — от `domain` к `api`. Обратных импортов нет.

```
chatbot/
├── domain/           сущности и контракты (не знает про FastAPI и БД)
│   ├── entities.py     Message, Conversation, BotReply, QuickReply, Action
│   ├── enums.py        Intent, MessageRole, AnswerSource
│   └── interfaces.py   Clock, ConversationRepository, KnowledgeBase, LLMGateway
├── knowledge/        факты о сервисе
│   ├── catalog.py      тарифы, шаги, тексты статей, приветствие
│   └── base.py         StaticKnowledgeBase — поиск по ключевым словам
├── repositories/     хранилища
│   └── in_memory.py    диалоги в памяти: TTL + LRU + потокобезопасность
├── llm/              шлюз к моделям
│   ├── prompts.py      системный промпт чат-бота
│   ├── gateway.py      ChatLLMGateway поверх backend.services.providers
│   └── streaming.py    StreamEvent / StreamEventType — события SSE
├── services/         прикладная логика
│   ├── greeting.py         приветствие и правило показа
│   ├── intent_resolver.py  определение намерения
│   ├── response_sanitizer.py  очистка и усечение ответа
│   └── orchestrator.py     основной сценарий диалога
├── api/              HTTP-контракт (тонкий слой)
│   ├── routes.py         эндпоинты
│   └── dependencies.py   DI-провайдеры FastAPI
├── session.py        хэширование клиентского идентификатора (152-ФЗ)
├── config.py         настройки модуля
├── models.py         Pydantic DTO
├── exceptions.py     иерархия ошибок
├── container.py      сборка зависимостей (composition root)
├── app.py            подключение к FastAPI
└── static/           виджет в браузере (ES-модули, без сборщика)
```

### Поток обработки сообщения

```
сообщение
  → валидация и rate limit
  → IntentResolver      (правила + морфология, без сети)
  → база знаний         (мгновенный ответ, если тема найдена)
  → LLM-шлюз            (только если уверенности не хватило)
  → ResponseSanitizer   (экранирование, обрезка)
  → BotReply
```

Ключевой принцип: **LLM не является обязательным**. При недоступной
модели чат-бот отвечает из базы знаний, а не показывает ошибку.

## API

| Метод | Путь | Назначение |
|-------|------|-----------|
| `GET` | `/api/chatbot/config` | конфигурация виджета |
| `GET` | `/api/chatbot/greeting` | приветствие + быстрые ответы |
| `POST` | `/api/chatbot/message` | отправить сообщение (обычный ответ) |
| `POST` | `/api/chatbot/stream` | отправить сообщение, ответ приходит потоком (SSE) |
| `GET` | `/api/chatbot/history` | история диалога |
| `POST` | `/api/chatbot/reset` | начать заново |
| `GET` | `/api/chatbot/health` | состояние модуля |

## Потоковая генерация (SSE)

`/api/chatbot/stream` отдаёт ответ по кускам, а не целиком. Формат —
стандартный SSE в соглашениях проекта (`data: {json}\n\n`, заголовки
`Cache-Control: no-cache`, `X-Accel-Buffering: no`, `Connection: keep-alive`).

```
event: meta    {"source": "llm", "intent": "pricing"}
event: delta   {"text": "Тарифы начинаются"}
event: delta   {"text": " от 99 ₽."}
event: done    {"message_id": "...", "quick_replies": [...]}
```

| Событие | Когда | Содержимое |
|---------|-------|------------|
| `meta` | перед первым фрагментом | источник ответа и распознанное намерение |
| `delta` | на каждый фрагмент | очередная часть текста |
| `done` | в конце | готовое сообщение и быстрые ответы |
| `error` | при сбое | текст ошибки вместо `done` |

Ключевые решения:

* `ChatOrchestrator.stream_message()` — **единственная** точка выбора
  источника ответа. Обычный `handle_message()` собирает тот же поток, поэтому
  потоковый и обычный ответы не могут разойтись.
* Ответ **из базы знаний тоже дробится на фрагменты** (`_emit_ready` →
  `_split_for_typing`) и отдаётся с паузой. Раньше он уходил одним куском,
  и в интерфейсе это выглядело как мёртвое серое поле вместо живой реплики.
  Разделители приклеиваются к предыдущему фрагменту, поэтому
  `"".join(фрагменты)` даёт исходный текст символ в символ.
* Событие `meta` отдаётся лениво — перед первым фрагментом. Если провайдер не
  отдал ни слова, `meta` не отправляется и метка источника остаётся честной.
* Failover между моделями допускается только **до первого фрагмента**:
  иначе посетитель увидел бы начало ответа одной модели и продолжение другой.
* Блокирующие провайдеры выполняются через `iterate_in_threadpool` — event
  loop не занимается.
* Во фронтенде разбор SSE сделан вручную поверх `fetch`
  (`services/StreamClient.js`), чтобы можно было прервать генерацию кнопкой
  «⏸». В ленте ответ рендерится инкрементально в `StreamingBubble`.

Скорость печати настраивается переменными `CHATBOT_TYPING_CHUNK_SIZE`
(размер порции в символах, по умолчанию 18) и `CHATBOT_TYPING_DELAY_MS`
(пауза между порциями, по умолчанию 20 мс).

## Настройки

Все параметры необязательны — переменные читаются с безопасными
значениями по умолчанию.

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `CHATBOT_ENABLED` | `true` | выключить модуль целиком (503) |
| `CHATBOT_AUTO_OPEN` | `true` | открывать окно при первом визите |
| `CHATBOT_GREETING_DELAY_MS` | `1200` | пауза перед автооткрытием |
| `CHATBOT_REMEMBER_CLOSE` | `true` | не показывать повторно после закрытия |
| `CHATBOT_MAX_MESSAGE_LENGTH` | `1000` | лимит длины сообщения |
| `CHATBOT_MAX_HISTORY_MESSAGES` | `10` | сколько сообщений уходит в модель |
| `CHATBOT_CONVERSATION_TTL_S` | `3600` | время жизни диалога в памяти |
| `CHATBOT_MAX_CONVERSATIONS` | `500` | потолок диалогов в процессе |
| `CHATBOT_LLM_ENABLED` | `true` | `false` — работа только на базе знаний |
| `CHATBOT_LLM_MODEL` | из основных настроек | модель для ответов |
| `CHATBOT_TYPING_CHUNK_SIZE` | `18` | размер порции «живой печати», символы |
| `CHATBOT_TYPING_DELAY_MS` | `20` | пауза между порциями, мс |

## Масштабирование

Модуль спроектирован под рост без переписывания:

* **Несколько инстансов.** Сейчас диалоги в памяти процесса. За
  `ConversationRepository` подставляется Redis — прикладной код не меняется.
* **Новые темы.** Добавить статью в `knowledge/catalog.py` и ключевое
  слово в `Intent` — остальное работает само.
* **Другая модель.** Реализация `LLMGateway` или смена цепочки провайдеров
  в `ChatLLMGateway._chain()`.
* **Интеграция с платежами.** У `BotReply` есть поле `actions` — кнопки
  с переходом к оплате или к разделу сайта.

## Безопасность и 152-ФЗ

1. Клиентский идентификатор сессии хэшируется с солью проекта (`session.py`).
2. История диалога живёт в памяти процесса, протухает по TTL и не пишется
   в базу.
3. Виджет хранит переписку в `localStorage` браузера и не отправляет её
   никуда, кроме сервера модуля.
4. Текст ответа модели экранируется перед рендерингом (`markdown.js`).
5. Текст от посетителя не попадает в логи — только метаданные.
